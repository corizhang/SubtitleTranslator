# AI 影视字幕翻译工具：技术基线

> 状态：初始基线  
> 日期：2026-08-13  
> 用途：作为产品设计、技术选型和后续开发评审的共同依据。

## 1. 产品目标

开发一个 Windows 桌面应用。用户拖入电影或电视剧视频后，应用从指定音轨识别原语言对白，翻译为中文，并生成与对白时间轴对齐的字幕。

首版支持：

- 拖入单个视频并选择音轨。
- 自动检测或手动指定源语言。
- 本地语音识别。
- 云端中文翻译。
- 单独中文字幕、原文字幕和原文加中文双语字幕。
- 视频同步预览和基础字幕校订。
- 导出 SRT、ASS 和工程文件。
- 处理中断后恢复，原视频默认不被修改。

首版不以实时翻译、完全无人校对、复杂特效字幕或在线字幕分享为目标。

## 2. 已确认的运行环境

- 操作系统：Windows 10 x64（10.0.19045）。
- GPU：NVIDIA GeForce GTX 1660 SUPER。
- 显存：6 GB。
- CUDA Compute Capability：7.5。
- NVIDIA 驱动：595.71。
- .NET SDK：10.0.102。
- 已安装 Microsoft.WindowsDesktop.App 9.0 和 10.0 运行时。

该 GPU 足以运行量化 Whisper 模型。完整版 large-v3 FP16 不作为默认模型，以避免显存不足和系统桌面、播放器争抢显存。

## 3. 核心技术决策

### 3.1 桌面技术栈

- UI：.NET 10、WPF、MVVM。
- 主业务：C#。
- 依赖注入与配置：Microsoft.Extensions.*。
- 项目数据：SQLite。
- 日志：结构化本地日志，必须脱敏。
- 视频预览：优先评估 LibVLCSharp.WPF，同时保留 mpv 适配可能。
- 音视频处理：随应用分发 FFmpeg 和 FFprobe，通过受控子进程调用。

Python 不是基础依赖。高级强制对齐或说话人识别需要 Python 生态时，以可选 Worker 形式接入，不进入 UI 和核心领域层。

### 3.2 识别策略

- 默认实现：Whisper.net + whisper.cpp CUDA runtime。
- 快速模式：small 多语言量化模型。
- 均衡模式：medium 量化模型。
- 高质量模式：large-v3-turbo 量化模型；需以实际显存和速度基准确认最终量化格式。
- GPU 不可用或模型加载失败时，允许回退 CPU，并明确提示速度变化。
- 所有识别结果必须保存原文、时间范围、置信信息和稳定 ID。

模型名称和量化格式属于部署配置，不允许散落硬编码在 UI 或业务逻辑中。

### 3.3 翻译策略

首版采用“本地识别 + 云端文本翻译”：

1. 视频和音频留在本机。
2. 仅向翻译服务发送必要的转录文本、上下文和术语。
3. 翻译请求和响应以稳定 SegmentId 关联，不由翻译模型生成时间戳。
4. 翻译服务通过接口适配，避免绑定单一供应商。
5. API 密钥使用 Windows Credential Manager 或等效安全存储，不写入工程文件、配置明文或日志。

完全离线翻译列入后续版本。6 GB 显存适合小型量化语言模型，但其影视翻译质量不能作为首版默认质量基准。

### 3.4 时间轴策略

时间轴来自识别和对齐层，翻译层只修改文字。

- 第一阶段使用 Whisper 分段时间戳。
- 长音频按约 5 分钟处理块识别，块间重置解码上下文；边界使用少量重叠并在合并时去重。
- 在识别前使用 VAD 排除明显静音/非语音区间，并保留原媒体时间偏移。
- 对连续完全相同或高度相似的异常输出设置检测阈值，触发丢弃、缩短块或严格参数重试。
- 分段器依据停顿、标点、语义、最大行长和阅读速度拆分或合并。
- 所有自动调整必须受原语音边界约束，并可撤销或重新生成。
- 高质量阶段增加词级时间戳、VAD 二次校准和 forced alignment。
- 视频存在固定音画偏移时，工程级提供全局字幕偏移设置。

### 3.5 字幕排版默认值

- 中文字幕最多两行。
- 每行建议 14～20 个汉字，可配置。
- 中文阅读速度默认上限建议 9 字/秒，可配置。
- 最短显示时间默认 800 ms。
- 双语 ASS 默认原文在上、中文在下。
- 避免字幕重叠；相邻字幕间隔可配置。
- SRT 以兼容性为先，ASS 用于双语字体、字号、颜色和位置样式。

这些是初始默认值，不是不可变标准，需要用真实影视样片验证。

## 4. 逻辑架构

```text
WPF Presentation
    |
Application / Use Cases
    |
Domain Model
    |
Infrastructure Adapters
    +-- FFmpeg / FFprobe
    +-- Whisper.net / CUDA
    +-- Translation Provider
    +-- SQLite Project Store
    +-- SRT / ASS Exporter
    +-- Video Player Adapter
    +-- Optional Python Alignment Worker
```

核心接口至少包括：

```csharp
public interface IMediaProbe;
public interface IAudioExtractor;
public interface ITranscriptionEngine;
public interface ITranslationProvider;
public interface ISubtitleSegmenter;
public interface ISubtitleExporter;
public interface IProjectStore;
public interface ISecretStore;
```

核心数据实体：

- `MediaSource`：视频、时长、音轨和基础元数据。
- `TranscriptSegment`：稳定 ID、源文本、起止时间、语言、说话人及置信信息。
- `TranslationSegment`：SegmentId、中文文本、翻译状态、模型信息和人工修改标记。
- `SubtitleCue`：最终显示时间、原文、译文、换行和样式。
- `SubtitleProject`：源媒体引用、设置、任务状态、术语表和生成物。

## 5. 处理流水线

```text
导入视频
 -> FFprobe 读取元数据与音轨
 -> FFmpeg 提取 16 kHz 单声道工作音频
 -> VAD/识别分段
 -> Whisper 本地转录
 -> 原文清理与字幕语义分段
 -> 带上下文批量翻译
 -> 阅读速度与时间冲突检查
 -> 生成 SubtitleCue
 -> 视频预览和人工校订
 -> 导出 SRT/ASS/VTT 或封装字幕轨
```

每个阶段都应写入可恢复的中间结果。失败后从最近的成功阶段继续，而不是重新处理整部视频。

## 6. 非功能要求

- 隐私：默认不上传视频或音频；上传文本前在界面明确说明。
- 可恢复：任务取消、进程崩溃或关机后可继续。
- 可追踪：记录处理阶段、模型、配置和错误，但不得记录密钥与完整敏感字幕。
- 可测试：核心分段、时间计算、格式导出不依赖 WPF，必须能单元测试。
- 可替换：播放器、识别引擎和翻译供应商通过接口隔离。
- 可发布：不要求最终用户安装 Python、CUDA Toolkit 或开发环境；所需运行库随应用打包或由安装器管理。

## 7. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 6 GB 显存不足 | 高质量模型加载失败 | 量化模型、显存预检、自动降级、CPU 回退 |
| 多人重叠或强背景音乐 | 识别和时间轴错误 | 低置信标记、VAD、后续强制对齐、人工校订 |
| 长音频上下文反馈循环 | 数分钟重复幻觉 | 5 分钟分块、NoContext、VAD、重复检测和块级重试 |
| 专有名词不一致 | 剧集翻译质量下降 | 项目术语库、人物表、跨集翻译记忆 |
| 翻译修改句意或合并段落 | 时间轴映射失效 | 强制结构化 SegmentId、响应校验、禁止模型生成时间戳 |
| FFmpeg 或模型分发体积大 | 安装和更新困难 | 组件版本清单、首次下载或可选组件包 |
| 云端费用不可控 | 用户成本风险 | 处理前估算、请求缓存、重试幂等、用量统计 |
| 视频路径变化 | 工程无法恢复 | 保存相对/绝对路径及媒体指纹，允许重新定位 |

## 8. 初始质量目标

- 30 分钟清晰对白样片能端到端生成中文和双语字幕。
- 正常取消任务后工程不损坏，重新打开可继续。
- 不因翻译失败改变已有原文时间戳。
- 所有导出字幕时间合法、不重叠、序号连续、编码为 UTF-8。
- GTX 1660 SUPER 使用推荐模型时不发生稳定性显存溢出。
- 对低置信、高阅读速度和时间冲突字幕提供可见提示。

## 9. 暂缓决策

以下事项需要在技术验证阶段用样片和原型决定：

- LibVLCSharp 与 mpv 的最终播放器选择。
- large-v3-turbo 的具体 GGML/GGUF 量化格式。
- 是否需要独立 VAD，以及采用哪个实现。
- 首个云端翻译供应商和具体模型。
- SQLite ORM 使用 EF Core、Dapper 还是轻量手写访问。
- 高级对齐采用纯 .NET 实现还是可选 Python Worker。
